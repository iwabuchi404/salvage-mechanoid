## 1. 目的

R1〜R6.5 で engine 側の内部構造（描画・エンティティ・ワールド）は整理された。しかし構造レビューの結果、**ゲームを成立させる側の基礎**が未整備であることが判明した。

具体的には、次の4つが「基礎」と呼べる形になっていない。

1. **イベント契約** — システム間通信の土台が無型で、契約不整合が実行時まで検出されない
2. **ステータスの正本** — 3箇所に分散し、導出ではなく一度きりの複写で繋がっている
3. **ターンの構造** — ターン番号も行動コストも行動順の概念も存在しない
4. **UI との境界** — UI をひとつ増やすたびに Game / uiStore / GameScreen の3箇所を編集する

本プランは、R7（Room ロック、スキャン、敵タイプ拡張）などの機能追加に入る前に、上記4つを「機能が乗る土台」として作ることを目的とする。

**本プランは機能追加ではない。** 新しいゲーム機能を実装せず、既存の挙動を維持したまま、今後の機能が乗る場所を作る。

## 3. 現状で「作れないもの」

本プランが解決する対象を、機能の言葉で明示する。以下はいずれも**現在の構造では実装できないか、実装しても正しく動かない**。

| 作りたいもの | 現状 | 対応フェーズ |
| --- | --- | --- |
| パーツを付け替えると性能が変わる | `PartsSystem.getStats()` の呼び出し元は初期化時の1箇所のみ。装備変更が伝播しない | BU-2 |
| 回復アイテムで HP が回復する | store だけ書き換え、`HealthComponent` は知らない。次の被弾で回復分が消える（**現在の不具合**） | BU-2 |
| 攻撃力アップアイテムでダメージが上がる | `AttackPowerComponent` が生成時スナップショット。UI 表示だけ増える（**現在の不具合**） | BU-2 |
| 毒などの状態異常が N ターン継続する | ターン番号が存在しない。継続を数える場所が無い | BU-3 |
| 素早い敵が2回行動する | 敵は登録順に必ず1回ずつ。`moveSpeed` は行動回数に影響しない | BU-3 |
| 新しい行動（待機・投擲・調べる）を足す | ターン進行トリガーが4つのイベントに分散。行動ごとに TurnSystem を編集 | BU-3 |
| ターンを消費しない行動を作る | 行動コストの概念が無い | BU-3 |
| 新しい UI パネルを足す | `Game` にコールバック追加 + `uiStore` にフィールド追加 + `GameScreen` にローカル ref 追加 | BU-4 |
| モーダル表示中に移動キーを無効化する | パネルの重なり順・入力ブロックの概念が無い | BU-4 |
| セーブして再開する | 永続化の口が無く、World / Entity がシリアライズ可能な形でない | 本プラン外（§7） |

## 5. 実行順序と依存関係

```text
BU-1（イベント契約）
  ↓ 後続すべての安全性を上げる
BU-2（ステータス）──┐
  ↓                 │
BU-3（ターン）───────┤
  ↓                 │
BU-4（UI 境界）←────┘
```

**BU-1 を最初に置く。** 前回のレビューでは優先順位を「ステータス → ターン → UI → イベント」としたが、実装順としては BU-1 を先に片付けるほうが安い。理由は次のとおり。

- BU-2 〜 BU-4 はいずれも新しいイベント（`stats_changed`、`turn_started`、UI 状態通知）を追加する。型付けを先にやれば、それらを最初から型付きで書ける
- 後から型付けすると、BU-2 〜 BU-4 で書いたイベントをもう一度触ることになる
- BU-1 単体は機械的な変更で、リスクが最も低い（3〜4 コミット）
- `ENTITY_MOVED` の事故（同名イベントの別ペイロード発行が実行時まで検出されなかった）と同種の事故を、以降のフェーズで防げる

BU-4（UI 境界）は最後に置く。BU-2 と BU-3 で「UI へ出すべき状態」が確定してから設計したほうが、ビューモデルを一度で決められる。

## 6. 共通の実装方針

`docs/REFACTORING_ROADMAP.md` §4.2 を継承する。

- 1 コミットでは 1 つの責務境界だけを変更する
- 公開 API やイベントを変える場合は、先に契約テストを追加する
- 新旧経路を一時的に併存させ、移行完了後に旧経路を削除する
- 旧 API 削除は移行コミットと分離する
- ファイル分割そのものを完了条件にせず、依存方向と所有権で判定する

本プラン固有の方針を追加する。

- **挙動を変えない**。既定値は現行と同じ実効値になるよう選ぶ。ゲームバランスの変更は行わない
- **現在の不具合の修正は、土台を作ってから行う**。回復アイテムと攻撃力アイテムの不整合は BU-2 の副産物として直る。個別に対症療法を当てない
- **既存の公開 API は、移行が完了するまで残す**。特に `Game` の `setOnXxx` は BU-4 の最終コミットまで維持する

## 7. 本プランのスコープ外

- **永続化（セーブ / ロード）**。BU-2 と BU-3 で状態の正本が定まった後、フロア再訪（R7-6）と合わせて別プランとする。ただし BU-2 / BU-3 の設計では「後からシリアライズできる形」を意識する
- R7 の機能実装そのもの（Room ロック、スキャン、敵タイプ拡張）
- ゲームバランス調整
- 新しい画像・音声資産の制作
- `RendererSystem` の再設計
- 全 System からの `Engine.instance` 一括排除（BU-2 / BU-4 で触る範囲のみ依存注入へ寄せる）

## 9. 中断・ロールバック方針

- 各フェーズの途中では旧経路を残し、移行先がテストを通ってから削除する
- 1 つのコミットで、ステータス境界（BU-2）とターン境界（BU-3）を同時に変更しない
- E2E 失敗時は次フェーズへ進まず、最後に成功したフェーズを基準線とする
- BU-2 と BU-3 は途中で止めても動作すること（旧経路が残っているため）を各コミットで確認する

## 10. 完了後の状態

本プラン完了時点で、次が成立していることを目標とする。

- イベントのペイロード不整合がコンパイル時に検出される
- プレイヤーの実効ステータスの正本が 1 つで、装備・アイテム・状態異常がすべて同じ経路で反映される
- `Player.ts` が Pinia ストアを参照しない
- ターン番号が存在し、行動コストで進行する
- 新しい行動を `TurnSystem` の変更なしで追加できる
- 新しい UI パネルを `Game.ts` の変更なしで追加できる
- UI がエンジンをポーリングしない

この状態になってから R7（Room ロック、スキャン、敵タイプ拡張）の仕様化へ進む。
